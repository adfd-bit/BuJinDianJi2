# 雷达障碍物监视工程调整

本次将原电机与雷达混合工程精简为雷达障碍物监视工程，保持项目名称和原 VS Code 左上角 ST-Link 启动入口。

## 应用变化

- 移除电机命令、速度控制、PWM、TIM1/TIM2 应用文件及初始化。
- 删除 USART1_RX DMA Channel5 与直接 DR 读取的双重接收路径，统一为 HAL 单字节中断接收。
- 固件按真实雷达完整扫描识别障碍物，输出小车坐标和前方阻挡状态。
- 按当前接线增加 USART2_TX / PA2、DMA Channel7，使用两份有明确所有权的缓冲输出换行 JSON。USART1 / PA10 仅接收雷达。
- 电脑由原始点云解析改为障碍物快照显示，失效时清除图标。
- 同步 CubeMX 与构建清单，保留启动、时钟、SysTick、SWD 和必要的 HAL 基础文件。

## 固定约定

实物 STL-06NBJ 输入是 `54 2C` /47 字节/12 点/CRC8，230400 8N1；固件同时保留旧 `A5 5A 6C` /108 字节/32 点/累加校验兼容。原工程解析格式与实物不符，是有效帧数一直为零的原因。

输出是协议 v1 JSON，每 100 ms 一条。小车中心为原点，X 向右、Y 向前，单位米；雷达右/前各 106 mm 偏移仅由固件补偿一次。

工程不包含电机自动绕行，也没有实时车辆定位。目标位置是可见表面点群中心。场地图中的车辆位姿仅用于显示。

## 验证边界

离线测试覆盖扫描启动与跨零、分组与坐标、异常后恢复、串口分段与超时、DMA 缓冲所有权。构建生成 ELF/BIN/HEX，内存占用以 map/size 为准。

硬件验收必须在开发板继续运行且雷达与 USB-UART 接好时检查真实 COM 报告，并用实物确认方向和距离。没有真实串口记录时，不应将离线通过称为真实雷达验证通过。

## 本次验证结果（2026-10-13）

- 固件构建通过，生成 ELF/BIN/HEX。`text=26672`、`data=92`、`bss=6644`；Flash 镜像 26764 字节（26.14 KiB / 64 KiB），RAM 的 data+bss 为 6736 字节（6.58 KiB / 20 KiB）。链接清单没有电机、TIM 或旧 RX DMA 应用对象；启动向量表保留芯片标准中断占位。
- C 算法测试通过 76 次快照检查，UART 恢复和双缓冲 DMA 测试通过；Python 的 15 项测试通过。覆盖半圈启动、跨零、首尾合并、最近八个目标、安装补偿、前方判断、错误恢复、超时、发送拥塞和 JSON 分段等。
- 使用 `.vscode/launch.json` 中的 GDB、ST-LINK Server 和 CubeProgrammer 路径，实际下载最终 ELF、复位，并命中 `main.c:30` 的临时断点，随后退出调试并恢复运行。日志在 `tests/validation/stlink_launch_20261013_211337_110/`。验证的是原入口使用的底层链路，本次没有自动点击 VS Code 按钮。原入口仍可使用；停在 `main` 后按 F5 继续运行。
- 从 Flash 回读全部 26764 字节，与构建 BIN 的 SHA256 一致：`32041938A007753A77B2C9A6DE1818A9BB0BCB7B252C62F6346E34AE124B7FCF`。回读文件为 `tests/artifacts/hardware-flash-readback.bin`。
- COM5 / CH340 经 PA2 实际采集 8 秒，81 条报告全部有效、80 个不同完整扫描、最多八个目标。JSON 错误、坏帧和丢字节均为 0；累计 UART 错误为 1，在采集与界面检查期间保持不变。记录为 `tests/artifacts/hardware-serial.jsonl`。
- 已确认两个视图都绘制真实障碍物，断开串口清除图标。截图为 `tests/artifacts/hardware-visualizer-vehicle.png` 和 `hardware-visualizer-field.png`。场地图只显示其当前范围内的目标。

实测周期性 `54 1F 00 00 00 41` 状态包现已单独解析，解决此前每约 500 ms 误报坏帧并清空图标的问题。仅接受当前确认的零状态内容，不能据此推断未确认的厂商状态码。

用户当前没有实车。本次完成的是开发板、真实雷达、USB-UART 和电脑界面验证；车体安装后的实物方向、安装偏移和距离精度尚未验收。输出仍按已约定的虚拟车体原点及右/前各 106 mm 偏移计算，不代表已获得车辆实时定位。
